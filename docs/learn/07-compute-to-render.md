# N-body 중력 시뮬레이션으로 배우는 WebGPU 컴퓨트

이 문서는 `src/demos/nbody/`를 읽는 순서대로 설명합니다. 데모는 2차원 원반 모양의 N개 물체가 서로 모두에게 중력을 받는 시뮬레이션을 세 가지로 구현해 비교합니다.

- `cpu-js`: 메인 스레드의 JS 이중 루프
- `gpu-naive`: 물체 하나당 스레드 하나, 모든 물체를 전역 메모리에서 직접 읽는 컴퓨트 셰이더
- `gpu-tiled`: 워크그룹 공유 메모리 타일을 쓰는 컴퓨트 셰이더

## 1. 왜 N-body가 GPU의 대표 사례인가

모든 쌍을 계산하면 한 스텝의 일이 N²입니다. N=16,384이면 2.7억 쌍이고, 쌍마다 뺄셈, 제곱, `inverseSqrt`, 곱셈, 누적을 합쳐 부동소수점 연산이 약 20개 듭니다.

중요한 것은 데이터 양입니다. 물체 N개의 위치는 N×8바이트인데 연산은 N²×20개입니다. 읽은 데이터 하나를 N번 다시 쓰니 연산 대 메모리 비율(산술 강도)이 N에 비례해 커집니다. 이런 일은 메모리 대역폭이 아니라 연산 장치 개수가 속도를 정하고, GPU는 연산 장치가 수천 개입니다. 반대로 합계 같은 작업은 읽은 값을 한 번만 쓰므로 대역폭에 막힙니다 (`compute-bench`의 reduction 참고).

물체는 서로 독립적으로 계산됩니다. 물체 i의 가속도는 "이전 스텝의 모든 위치"만 읽으므로 스레드 N개를 동시에 돌려도 순서를 신경 쓸 필요가 없습니다.

## 2. 물리와 적분 규칙

- 가속도: `a_i = (GM/N) · Σ_j (p_j - p_i) / (|p_j - p_i|² + ε²)^{3/2}`. ε는 softening입니다. 거리가 0에 가까워도 값이 터지지 않고, i=j 항은 0이 되어 따로 빼지 않아도 됩니다.
- 적분: symplectic Euler(반암시적 오일러). `v ← v + a(p)·dt`, `p ← p + v·dt`. 새 속도로 위치를 갱신하는 것이 일반 오일러와의 차이이고, 이 덕분에 에너지가 길게 보았을 때 발산하지 않습니다.
- `dt = 1/60`은 고정입니다. 실제 시계를 쓰면 프레임마다 결과가 달라져 CPU와 GPU를 비교할 수 없습니다.
- 초기 상태는 `core/rng`의 mulberry32로 만든 원반입니다. 각 물체는 둘러싼 질량 안쪽의 원 궤도 속도로 돕니다.

## 3. 상태는 왜 두 버퍼인가

스텝 중에 스레드 i가 자기 위치를 덮어쓰면 아직 계산 중인 스레드 j가 새 위치를 읽습니다. 그래서 상태를 버퍼 A, B로 두고 A에서 읽어 B에 쓴 뒤 다음 스텝은 반대로 합니다(핑퐁). `createGpuSim`의 `bindGroups`가 이 두 방향을 미리 만들어 둡니다. CPU 버전 `stepCpu(src, dst)`도 같은 구조입니다.

## 4. 순진한 커널과 타일링 커널

순진한 커널은 스레드마다 `src[j]`를 N번 읽습니다. 같은 워크그룹의 스레드들이 같은 `src[j]`를 동시에 읽으니 캐시가 도와주긴 하지만, 전역 메모리 읽기 횟수는 N²입니다.

타일링 커널(GPU Gems 3 31장)은 이렇게 합니다.

1. 워크그룹의 스레드 256개가 각자 물체 하나를 `var<workgroup> tile`에 올립니다.
2. `workgroupBarrier()`: 모두 올릴 때까지 기다립니다.
3. 스레드마다 `tile`의 256개 물체와의 힘을 계산합니다. 읽기는 빠른 공유 메모리입니다.
4. `workgroupBarrier()`: 모두 다 쓸 때까지 기다립니다. 이 두 번째 배리어가 없으면 빠른 스레드가 다음 타일을 덮어씁니다.
5. 다음 타일로 반복합니다.

전역 메모리 읽기는 N²에서 N²/256으로 줄어듭니다. 배리어는 워크그룹 안의 모든 스레드가 도달해야 하므로 `if (i >= n) return;`처럼 일찍 빠져나가면 안 됩니다. 코드에서 범위 밖 스레드는 로드와 쓰기만 건너뛰고 배리어는 지납니다. 마지막 타일이 덜 찼을 때를 위해 안쪽 루프 상한은 `min(256, n - base)`입니다.

타일링의 이득은 GPU마다 다릅니다. 같은 주소를 읽는 스레드의 요청을 하드웨어가 합쳐 주면 순진한 커널도 빠르고 (이 데모를 돌린 M1이 그랬습니다), 이 구현은 `vec2f` 타일 하나만 쓰며 안쪽 루프를 펼치지 않았으므로 최적화의 끝이 아닙니다.

## 5. 프레임마다 읽어오지 않는 이유, 한 인코더

상태가 스토리지 버퍼에 있고 렌더 패스의 버텍스 셰이더가 같은 버퍼를 `array<vec4f>`로 읽습니다. CPU는 위치를 알 필요가 없으므로 `mapAsync` 읽기가 없습니다. `frame()`은 한 커맨드 인코더에 컴퓨트 패스와 렌더 패스를 차례로 기록하고 한 번 제출합니다. 같은 큐 안의 패스는 순서대로 실행되고 컴퓨트 쓰기는 렌더 읽기 전에 보입니다.

읽어오는 곳은 `verify.ts` 하나입니다. 정확도를 보려고 10스텝 뒤 한 번만 `copyBufferToBuffer` 후 `mapAsync`합니다.

`cpu-js`는 상태를 매 프레임 `writeBuffer`로 올려 같은 렌더러로 그립니다. 그래서 세 변형의 그리기 비용이 같고, 차이는 시뮬레이션 계산에서만 나옵니다.

## 6. 숫자 읽는 법

- "주사율에서 유지되는 최대 N": 중앙값 간격, 드롭 비율, 실효 프레임 시간이 모두 기준 안인 가장 큰 N입니다. 배가 후 이분 탐색이고 상한은 262,144입니다. 일이 N²이므로 N이 2배면 필요한 시간이 4배입니다.
- 스텝/초, 쌍/초: `스텝/프레임 × 1000 / 실효 프레임 시간`, 거기에 N²를 곱한 값입니다. 변형이 주사율을 따라가는 동안에는 rAF가 60Hz로 묶으므로 이 값은 하한입니다. GPU가 남는 N에서는 "스텝/프레임"을 올려야 진짜 처리량이 보입니다.
- gpu 시간: 컴퓨트 패스 시작부터 렌더 패스 끝까지의 타임스탬프 차입니다. 렌더 비용이 포함됩니다.
- 정확도 검증: 같은 시드로 N=4096, 10스텝을 CPU(f64 누산)와 각 GPU 커널(f32)로 돌려 최대 절대 위치 오차를 봅니다. 중력은 가까운 만남에서 반올림 차이를 키우므로 스텝을 길게 잡으면 정상인 차이와 버그를 구분하지 못합니다. 이 머신에서 오차는 3e-5 px(f32 한 칸)이었고 허용치는 1e-3 px입니다.

## 7. 이 머신에서 나온 값 (헤드리스 스모크, 성능 주장 아님)

Apple M1, 헤드리스 Chromium, 주사율 약 60Hz, 다른 GPU 작업이 동시에 돌던 상태에서 한 번씩 잰 값입니다. 숫자는 흔들리므로 경향만 보세요.

| 변형 | 주사율 유지 최대 N | N=8,192 실효 프레임(ms) | N=65,536 실효 프레임(ms) |
|---|---|---|---|
| cpu-js | 약 2,750 | 120.0 | 측정 안 함 |
| gpu-naive | 약 26,000 | 17.0 (주사율에 묶임) | 102.6 |
| gpu-tiled | 약 25,000 | 16.9 (주사율에 묶임) | 105.1 |

- CPU는 주사율을 겨우 넘는 N=2,750에서 이미 한계입니다. 같은 N²인데 GPU는 약 10배 큰 N까지 유지합니다. 이는 쌍 수로 약 90배입니다.
- 순진한 커널과 타일링 커널은 이 머신에서 구분되지 않습니다 (측정 오차 안). N=65,536에서 두 커널 모두 약 100ms, 즉 초당 약 4×10^10 쌍(약 0.8 TFLOP/s로 환산)입니다. M1은 같은 주소를 읽는 스레드의 읽기를 캐시가 합쳐 주고 쌍당 연산이 많아서, 이 커널은 메모리보다 연산에 막힌 것으로 보입니다 (추정). 타일링이 확실히 이기는 구조는 별도 GPU에서 확인해야 합니다.
- N=8,192에서 GPU 변형은 gpu 시간이 5ms 안팎이라 주사율에 가려져 실효 프레임이 같습니다. 이런 구간의 스텝/초는 하한이므로 "스텝/프레임"을 올려 보세요.

## 8. 해보기

- `gpu-tiled`의 `TILE`(kernels.ts)을 64, 128로 바꿔 최대 N이 어떻게 달라지는지 봅니다.
- 타일 로드 뒤 두 번째 `workgroupBarrier()`를 지워 보세요. 검증이 실패해야 합니다.
- "스텝/프레임"을 8로 올려 GPU 변형의 스텝/초를 비교해 보세요.
- softening ε를 1로 줄이면 가까운 만남에서 CPU와 GPU의 차이가 어떻게 커지는지 검증 오차로 확인합니다.
